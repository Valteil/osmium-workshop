# Dataset Tag Studio — Development Context & Architecture

Local Electron desktop app for managing AI training dataset tags. No network calls, no uploads — everything stays on disk, with one opt-in exception: the WD14 Autotagger talks to a user-configured local ComfyUI instance (see Feature Overview / Security Notes).

## What This Project Is

A tag editor for managing thousands of images and their captions (stored as `.txt` files in the same folder), for preparing LoRA/Stable Diffusion datasets. Browse images, edit/add/remove tags per image or bulk, compare tags across images, find/merge duplicates, undo any edit with full history. Also: themes, achievements, shop (cosmetic), zoom/font-size scaling.

## Architecture

**Source is TypeScript** (`src/`). `main.js`, `preload.js`, and `renderer/app.js` are **generated files** — never hand-edit them; edit `src/` and run `npm run build` (or `npm run refresh-app` for the dev loop, see below).

**Backend:** Electron (`src/main.ts` → `main.js`, `src/preload.ts` → `preload.js`)
- `main.ts`: window management, file I/O, IPC handlers for restart/page-zoom/GitHub-package-export/WD14-ComfyUI-bridge
- `preload.ts`: minimal security bridge — only exposes `restartApp()`, `setZoomFactor()`, `generateGithubPackage()`, `wd14GetModels()`, `wd14TagImage()`
- No Node.js APIs exposed to the renderer

**Frontend:** `src/renderer/index.ts` is the composition root (~1,090 lines: core app state, folder loading, module wiring) plus its extracted modules, bundled by esbuild into `renderer/app.js`.
- `renderer/index.html`: structure only, hand-authored
- `renderer/app.js`: BUILD OUTPUT — do not hand-edit
- `renderer/styles.css`: all styling (25 themes + night/day mode), hand-authored
- `renderer/data/`: Danbooru wiki.json.gz (definitions) + all_tags.json.gz (tag vocabulary)

**Key file locations:** working source is `src/main.ts`, `src/preload.ts`, `src/renderer/*.ts` + `package.json`.

**Layout you'll see at the project root:** the built portable app (`Dataset Tag Studio.exe`, `resources/`, `locales/`, Chromium runtime files, `data/`) sits loose at the project root alongside `src/`, `node_modules/`, etc. — this is deliberate, not clutter. `npm run refresh-app` regenerates it from `dist/win-unpacked`; `run-portable-dev.bat` launches it. All gitignored, not source.
- `Shippable/` — release artifacts only, from `npm run dist:zip` (`compression: "normal"` by default in `package.json`; pass `-- --config.compression=store` to skip compression for a quick throwaway build). Only run this when an actual release is wanted; `refresh-app`/`npm start` cover routine verification.
- App data is portable, next to the built app's own folder (`data/`). The AppData-based path (`%APPDATA%\Dataset Tag Studio\tool\`) only applies to `npm start` dev-mode runs, not packaged builds.
- Don't reintroduce `DROP_UPDATES_HERE`, `applyUpdateBundle`, or `relaunchApp` — deliberately removed; updates are now a fresh zip download + moving `data/` over.

## Tauri Port — DISCONTINUED (2026-09-13)

A second build target (`tauri-port/`, a Rust backend reusing this same
`renderer/` folder) was built and maintained alongside Electron for a
while, but is now retired and deleted from this repo. Reason: keeping a
hand-translated Rust mirror of every `main.ts`/`preload.ts` change in sync
was too high a maintenance burden alongside actively developing the
Electron app — every new IPC handler (the SynthDat Overseer work in
particular) meant hand-porting the same logic to `reqwest`/Rust and
re-verifying it via CDP, which slowed real feature work without a
commensurate payoff at this project's current stage. This app is
**Electron-only going forward.**

Do not casually resurrect `tauri-port/` from git history and resume the
old "port every change" policy — if cross-platform reach becomes a real
requirement again, that's a deliberate new decision to make (and possibly
a different approach than a hand-maintained parallel Rust backend), not a
default to fall back into. The old port's own approach (`tauri-shim.js`
mapping `window.electronAPI` onto `window.__TAURI__`, a Rust
`src-tauri/src/wd14.rs` mirroring the ComfyUI bridge, `renderer/` shared
verbatim between both builds) is preserved in git history if it's ever
worth referencing again — see the commit that removed `tauri-port/`.

## TypeScript Build

- `npm run build` = `build:main` (tsc → `main.js`/`preload.js`) + `build:renderer` (tsc type-check, then esbuild bundles `src/renderer/index.ts` → `renderer/app.js`). Wired as a `pre*` step on `start`/`dist`/`dist:zip`/`dist:dir`/`refresh-app` — runs automatically.
- Every renderer module carries `// @ts-nocheck` — real type annotations are a possible later increment, module-by-module, never all at once.
- `src/renderer/global-types.ts` declares `window.electronAPI`'s shape. Named `.ts`, not the conventional `.d.ts` — electron-builder's `files` whitelist hardcodes `**/*.d.ts` into its default-ignore list (can't be overridden by an explicit include; verified), which silently dropped this file from every packaged build and broke `tsc`'s `window.electronAPI` typing for anyone rebuilding from a "Generate GitHub package" export. A plain `declare global {}` block works identically regardless of extension, so renaming was simpler than fighting electron-builder's ignore precedence.
- Renderer modules, one ES module each, imported into `index.ts`: `dom.ts` (DOM lookups — the single source of `$('id')` calls), `shared-ui.ts` (toast/panel show-hide/confirm modal/persistent dropdown/positionMenu/escapeHtml/pinch-zoom+long-press), `themes.ts`, `docks.ts`, `settings.ts`, `power-tools.ts`, `quick-merge.ts`, `tag-pruner.ts`, `tags-autocomplete.ts`, `achievements.ts` (stats/wallet/shop), `favorites.ts`, `edit-log.ts` (edit log panel + Stats tab charts), `tags-edit.ts` (add/remove tag, undo/redo, disable/restore, save-to-disk), `master-tag-control.ts`, `tag-details.ts` (wiki lookups), `tag-index.ts` (tag frequency list + gallery filtering), `view.ts` (gallery/compact/single rendering, chips, image modal, context menus), `random-facts.ts` (empty-state fact button, self-contained), `wd14-tagger.ts` (WD14 Autotagger — ComfyUI bridge settings, bulk/single-image triggers, review-before-apply).
- **Module convention:** `index.ts` owns core cross-cutting state (`entries`, `dirHandle`, `selectedTags`, `galleryFilter`) and wires every module together via small `init*(deps)` calls — never a circular `import`. State a module owns that another file needs to *reassign* (not just mutate) must be exposed via an exported reset function (e.g. `resetUndoRedo()`), never a raw mutable export reassigned from outside. State `index.ts` owns that a module needs to *read* must be passed as a getter (`() => entries`), not a captured snapshot, since it may be reassigned wholesale elsewhere (e.g. `entries = []` on folder load).

## Critical Constraints

- **Floating panels** (Favorites, Log, Achievements, Shop, Settings, Tag Details, Theme Custom) live OUTSIDE `#app`, as `<body>` siblings — CSS `zoom` on `#app` scales the element's box independently of its container, so any new floating overlay must follow this pattern too. `#app` uses `100%/100%`, not `100vw/100vh`, for the same reason.
- **Font-size zoom is native Electron zoom**, not CSS zoom: `applyAppZoom(factor)` (`settings.ts`) → `window.electronAPI.setZoomFactor()` → main process. Clamped 0.86–3x server-side. Never add a CSS-zoom-based scaling path.
- **Night/day mode is an HSL lightness inversion** (`100 - L`, keep hue/saturation) in `themes.ts`, not a fixed palette swap. Custom theme is excluded (already user-controlled). Theme (and night-mode) application happens TWICE at startup, deliberately: `index.html`'s inline pre-paint `<script>` applies the saved theme before first paint (sets `window.__dtsPreThemed`), then `index.ts`'s `initTheme()`/`initNightMode()` check that flag and skip redoing the work (calling `syncNightModeFromPrePaint()` instead of re-inverting) — re-inverting an already-inverted display returns the wrong colors. Any change to the inversion formula in `themes.ts` must be mirrored in `index.html`'s inline script (a necessary duplicate, since it runs before any ES module loads).
- **No network font dependency** — system-font stacks only (no `fonts.googleapis.com`). Custom-font field in Settings covers user-installed fonts.
- **Text/language tagging:** Japanese and each foreign language are independent, non-exclusive selections (a page can have Japanese AND English AND Russian text at once). `syncTextPanelTags()` (`view.ts`) reconciles `draft.foreignLangs` (a `Set`) against the entry's "* text" tags independently of `draft.isJapanese`'s bare "text" tag — neither selection clears the other. No "Apply" button; every text-panel control writes tags immediately via its own change/click handler calling `syncTextPanelTags()`. Don't reintroduce single-select exclusivity or a staged "configure then Apply" step here.
- **Unsaved-changes close guard goes through main-process IPC, not `beforeunload`** — Electron doesn't implement the browser's "Leave site?" prompt; `preventDefault()` on `beforeunload` just silently blocks the close with no feedback. Pattern in place: `main.ts`'s `win.on('close', ...)` always `preventDefault()`s and sends `request-close` over IPC; the renderer checks dirty entries, shows `showConfirmModal()` if needed, then calls `electronAPI.confirmClose()` which sets `win.__closeConfirmed` and re-closes. Any future "warn before X" guard needs this same shape, not a bare DOM event.
- **Adding a new theme:** every theme needs its own `--accent-flair` var (a `THEME_VARS` entry in `themes.ts` — omitting it silently freezes that var under night mode) that's a genuinely distinct hue from `--accent-manual`, plus at least one non-color flourish (texture, animation, card-corner shape, button shape) distinct from other themes in the same visual cluster. `PREMIUM_THEMES`' `swatches` array must equal exactly `[--bg-base, --accent-manual, --accent-flair]`. Before adding a theme, convert its planned bg-base/accent-manual/accent-auto to HSL and compare hue against every existing theme in the same light/dark bucket to avoid near-duplicate palettes. The hover-fill button effect (`--accent-flair` sliding in from the left on hover) is reserved for epic/legendary shop tier — its selector must exclude `.img-menu-btn`, `.compare-img-cell button`, and every `all: unset`-based button class (`.ctx-item`, `.pdrop-item`, `.dock-collapse-btn`, `.chip button`, `.exclude-badge button`, `.lang-common-chip button`); grep the file for `all: unset` and `position: absolute` before adding any new broad theme-wide `button:not(...)` selector. A NEW epic/legendary theme still gets its own `html[data-theme="..."]` line added to those same selector groups — don't rely on `html.theme-refined` for that, it only covers themes individually upgraded via Refine Theme (see below), not the theme's own native tier.
- **Refine Theme (shop):** any non-epic/legendary theme can individually buy the same hover-fill effect via the Shop's 🔨 Refine Theme button, for `epicThemePrice() - themeOriginalPrice(themeId)` Edibits (`themes.ts`). Refined theme ids persist in `themes.ts`'s `refinedThemes` (localStorage `dts-refined-themes`), and `applyTheme()` toggles a generic `html.theme-refined` class based on membership — that class is OR'd into the same three hover-fill selector groups as the five hardcoded epic/legendary theme names in `styles.css`, so it needs no per-theme CSS of its own. Refine Theme's reward is two effects, not one: the hover-fill button flood above, plus a gallery-card hover tilt (`transform: rotate(-0.6deg) translateY(-2px)` + a dark drop shadow) borrowed from Vintage Paper's own one-off flourish — both live in the same epic/legendary + `html.theme-refined` selector group (`styles.css`, right before "End themes"), so a future third reward should join that same group rather than starting a new one.
- **Two separate Settings toggles gate theme effects, at different scopes — don't conflate them:**
  - **Suppress Theme Upgrade** (`suppressThemeUpgradeToggle`, `localStorage['dts-suppress-theme-upgrade']`) hides the Shop's Refine Theme button AND withholds the effects Refine Theme grants — but ONLY those, and only from themes that got them via refinement. It's implemented as `html.suppress-theme-upgrade`, and every `html.theme-refined` selector in the hover-fill/card-tilt groups is actually `html.theme-refined:not(.suppress-theme-upgrade)` — the five native epic/legendary theme lines in those same groups are untouched, since their effects were never something Refine Theme granted.
  - **Disable theme flourishes** (`disableThemeFlourishesToggle`, `localStorage['dts-no-theme-flourishes']`, `html.no-theme-flourishes`) is unscoped — a motion-sensitivity switch that kills hover-tilt and hover-fill on EVERY theme regardless of tier or refinement (`html.no-theme-flourishes .card:hover{ transform:none!important }` / `html.no-theme-flourishes button::after{ display:none!important }`, `styles.css` right before "End themes"), plus every ambient per-theme animation (the `flair*`-keyframed rules — cyberpunk/bioluminescent/solarflare/blood-moon's pulsing glow, amethyst's topbar sweep, rose-gold's button shimmer, aurora-borealis's drifting background) via a shared `--flair-play` custom property each such rule's `animation-play-state` reads, flipped to `paused` by this one class instead of threading a `:not()` guard through every existing selector. It deliberately does NOT touch each theme's static, non-animated color accents (glows/gradients/textures) — not a motion trigger, and disabling every one individually would mean editing nearly every theme's own CSS block. Any NEW ambient `flair*`-style animation must add `animation-play-state: var(--flair-play);` to stay covered by this toggle.
- **WD14 Autotagger network calls happen in `main.ts`, never as a renderer-side `fetch()`.** ComfyUI's `server.py` rejects cross-origin requests whose `Origin` doesn't match `Host` (its `origin_only_middleware`), and separately Chromium enforces CORS on the response regardless — this app's renderer origin can satisfy neither without `--enable-cors-header` on the ComfyUI side, which isn't something to depend on. The main process has no such restriction, so `wd14-get-models`/`wd14-tag-image` IPC handlers do the HTTP work (upload/image → prompt → poll history) and hand the renderer only the parsed result. Any future "call a local HTTP server" feature should follow this same shape, not a direct renderer fetch.
- **All WD14 Autotagger settings live in Tag Overseer** (`wd14-tagger.ts`'s expandable "⚙ WD14 settings" section) — persisted to `localStorage['dts-wd14-settings']`. The per-image 3-dot menu's "Tag this image with WD14" only triggers a single-image run using whatever's configured there; it does not duplicate any settings UI. The model dropdown is always scraped live from ComfyUI's `/object_info/WD14Tagger|pysssss` (`wd14-get-models`) rather than hardcoded, since the app holds no models itself.
- **SynthDat Overseer's node-id map is fixed to one specific ComfyUI workflow — never re-derive it from a UI-format `.json` export.** The workflow-editor format (`nodes`/`links`, packed subgraphs) is NOT what `/prompt` accepts; the correct approach (already done) was queuing the workflow once from a live ComfyUI instance and pulling the real submitted graph back out of `GET /history/<id>`, which resolves subgraphs and mute/bypass state the same way ComfyUI's own compiler would. The 15 prompt-category text fields (`21` Global, `8` Rating, `11` Character, `12`/`15`/`18`/`9` Hair/Face/Chest/Body, `6`/`20`/`14`/`7` Clothes/Limbs/Sexual/Pose, `10`/`13`/`17` Extra/Effects/Scene, `16` Negative) feed `52` (Positive) via 4 concatenation nodes; `41`/`51`/`237` are the diffusion model/Main LoRA/LoRA-stack nodes (`237` chains additional cloned stack nodes past its own 4 slots — see `buildPromptFromFields()`); `239` LoadImage → `238` Image Resize (rgthree, does the actual resize+pad; also feeds ComfyUI's own `246` PreviewImage) → `240` AnimaLLLiteApply (consumes `238`'s padded output, NOT `239`'s raw one — a bug in this app's original wiring pointed it at the raw image instead, fixed this session) → `243` ImpactSwitch (always forced to `select:2`, CNET-on) is the ControlNet path; "skip reference image" deletes `239`/`238`/`246`/`240`/`243` together (238/246 both transitively depend on 239, so leaving either in after deleting 239 fails prompt validation — 246 is itself an independent "output node" ComfyUI validates regardless of what `192`/SaveImage needs) and repoints `158:53`/`158:54` at the LoRA stack's own output; `165`/`227` are the two passes' seeds, `195` is pass-2's BasicScheduler (denoise/steps/scheduler), `168:167` is the live sampler-selector KSamplerSelect, `174:171`/`174:172` are width/height. **1-Pass vs 2-Pass is presence/absence of nodes, not a flag** — there is no "mode" concept in the API format; 1-Pass deletes `190`/`191`/`195`/`227`/`224` from the cloned template and repoints `192` (the one always-on SaveImage) at `["176",0]` (pass-1's decode) instead of `["191",0]`. When 2-Pass IS enabled, `buildPromptFromFields()` also clones a second SaveImage, `192_pass1` (inputs: same `filename_prefix` as `192`, `images: ["176",0]`) — this exists purely so the app can fetch BOTH the pass-1 and pass-2 (refined) results from the same generation and let the user pick between them after the fact (see Feature Overview's SynthDat Overseer entry, and `main.ts`'s `synthdat-queue-and-fetch`, which fetches `record.outputs['192_pass1']` alongside `'192'` whenever it's present and returns it as `pass1ImageBytes`).
- **TAESD live preview + Stop button need a raw WebSocket to ComfyUI, opened from `main.ts`, not the renderer** — same CORS/origin reasoning as the WD14 bridge above, applied to `/ws?clientId=...`. Preview frames arrive as ComfyUI's documented binary format (4-byte BE event type, 4-byte BE image type, then raw JPEG/PNG bytes) and get relayed to the renderer via a plain `event.sender.send(...)` WHILE the `synthdat-queue-and-fetch` invoke() is still pending — a normal, valid Electron pattern (main→renderer push events alongside an in-flight two-way invoke), not something to "fix" into a single round trip. Stop calls ComfyUI's `/interrupt` AND sets a shared `activeSynthdatGen.cancelled` flag the polling loop checks every iteration, so it returns immediately rather than waiting for `/history` to eventually reflect the interruption.
- **A new runtime `dependencies` entry (e.g. `ws`, added for the above) is NOT automatically bundled into the packaged app** — this project's `package.json` `build.files` list is an explicit whitelist (`main.js`, `preload.js`, `renderer/**/*`, `src/**/*`, etc.) with no blanket `node_modules/**` entry, unlike electron-builder's usual default behavior. Any new npm dependency main.ts actually `require()`s at runtime needs its own `node_modules/<pkg>/**/*` line added to that list, or it silently works in dev (`npm start`) and throws `Cannot find module` only in the packaged build. Verify with `npx asar list resources/app.asar | grep node_modules` after `refresh-app` (Windows asar paths use backslashes, not forward slashes).

## Data Flow

**Tag loading & normalization:** on folder open, each `image.jpg`/`.png` pairs with `image.txt` (UTF-8, one tag per line). On load: underscores → spaces, collapse whitespace, trim; stored as `entries[i].tags`. On save: spaces → underscores, written back to `.txt`. (One-way: a tag that ends up with underscores in-app is treated as containing a literal space, by design.)

**Edit history:** every tag add/remove logs to `folderStats.edit_log`; undo/redo stack is global, not per-image; logs persist to `_tag_edit_log.json` in the dataset folder.

**Favorites/Achievements/Wallet:** persisted to `localStorage`, scoped by folder hash (`_dts_meta.json` stores folder UUID). Achievements unlocked → Edibits earned (stored per-folder in `.json` files).

**Unsaved Approved (SynthDat Accept staging) — a third file-location state alongside active/Disabled.** `entry.pendingApproval` (boolean, alongside `entry.disabled`) marks an entry whose image lives in the dataset's `Unsaved Approved/` folder rather than the root — created by SynthDat Overseer's Accept (`writeImageEntry()`, synthdat-overseer.ts), which writes BOTH the image AND a `.txt` of its current tags into that staging folder immediately (accepting an image means trusting its tags as they stand at that moment, so there's no reason to risk losing them to a crash before the next Save the way a purely in-memory edit would). `entry.dirty`/`pendingApproval` still start `true` regardless — this immediate write is a safety net into the STAGING location, not the real save. `buildEntry()` (index.ts) sets `dirty: pendingApproval` — a pending-approval entry always starts dirty by definition. `saveAllDirty()` (tags-edit.ts) special-cases these: instead of its normal in-place `.txt` write, it calls `promotePendingApproval()`, which moves both files from `Unsaved Approved/` into the dataset root (writing a fresh `.txt` there, superseding the staged one) and clears the flag — this is what "saving" actually means for one of these; any tag edits made AFTER Accept but before that eventual Save still only live in memory until then, same limitation as any other dirty entry. `moveEntry()` also special-cases them (a user manually rejecting/disabling one via the 3-dot menu before it's ever saved needs its CURRENT location read from `entry.pendingApproval`, not assumed to be the root). Has its own view (`viewPendingApprovalBtn` → `switchView('pendingApproval')` → `galleryFilter.pendingApprovalView`, in `view.ts`/`tag-index.ts`'s `passesFilter()` — mutually exclusive with `disabledView`, both excluded from the normal grid/compact/single filter), positioned before the Disabled view in the toolbar. `loadFolder()` (index.ts) scans `Unsaved Approved/` on open the same way it scans `Disabled/`, so a leftover image AND its tags from a crash/close-without-saving a previous session both survive. Reject and the auto-reject-the-leftover-pass path (below) are NOT staged this way — they write straight to the root and save immediately, per explicit design ("Disableds are always saved immediately").

**SynthDat Accept/Reject pass-choice semantics.** When 2-Pass generated both a pass-1 and pass-2 (refined) result (see the `192_pass1` node below) and the user picked one via `selectPass()`: **Accept** keeps the selected pass (staged in Unsaved Approved/, per above) and also writes the OTHER pass straight to Disabled/ (`otherPassBytes()`/`acceptImage()`, synthdat-overseer.ts) — nothing generated is ever silently discarded. **Reject** sends BOTH passes to Disabled/ (`rejectImage()`) — there's no "keep" decision being made, so nothing should survive as an active/staged entry. **Starting a new generation while a previous one is still un-decided** (`autoRejectPendingIfAny()`, called at the top of `generate()`) auto-rejects every pass the previous run produced into Disabled/ before proceeding, instead of silently losing it when `clearPreview()` resets state for the new run.

**Autosave** (Settings ▸ Saving, `autosaveToggle`, `localStorage['dts-autosave']`): off by default. When on, `markDirty()` (tags-edit.ts) debounces a call to `saveAllDirty(true)` (silent — no toast) ~1.2s after the last edit, instead of only saving on a manual Save click. Considered safe specifically because every edit is already in the Edit Log with its own undo regardless of whether the `.txt` has been physically written yet.

**Retroactive Merge/Void rule edits are a dirty/saveable action, same as a tag edit — not an instant disk write.** `tags-edit.ts`'s `rulesDirty` flag (`markRulesDirty()`/`resetRulesDirty()`) folds into the exact same dirty indicator, Save button, and autosave debounce as `entry.dirty` (`dirtyCountEl` shows `(N + rules)`/`(rules)` when applicable, `btnSave` enables for either), and `saveAllDirty()` is what actually calls `canonical-tags.ts`'s `saveCanonicalRules()`. `canonical-tags.ts` can't import `tags-edit.ts` back (already imported the other way), so it calls an injected `markRulesDirty` dep (`initCanonicalTags()`) instead of writing to disk directly — every rule mutation site (`commitRuleChange()`, `registerMergeRule()`/`registerVoidRule()`, rule deletion, naming a new rule) was switched from `saveCanonicalRules()` to this dep. The ONE exception: `loadCanonicalRulesForFolder()`'s first-run bootstrap (reconstructing rules from `editLog` history for a dataset that predates this feature) still saves immediately — it's not a user edit needing a save prompt, just persisting a derived migration. Every unsaved-changes guard (Quit/Restart/Unload/Reload/switch-dataset) checks `rulesDirty` alongside `entry.dirty` via `index.ts`'s shared `unsavedChangesDescription()` helper — don't add a new guard that checks `entries.filter(e=>e.dirty)` alone without also considering this.

**Reload dataset** (`btnReloadDataset`, File menu): re-runs `loadFolder()` against the already-open `dirHandle` — same unsaved-changes confirm guard as Unload/Quit/Restart (discarding unsaved edits would otherwise happen silently). Picks up files changed/added outside the app and any leftover Unsaved Approved images from a previous session.

## Key Code Locations

- **Theme picker dropdown (custom, not a native `<select>`):** `initThemeDropdown()` in `src/renderer/themes.ts` — `#themeSelect` stays hidden in the DOM as the value/option store; the visible control is a `.pdrop`-style div immune to native-select scroll-dismissal (see Known Pitfalls)
- **Day/Night toggle:** `toggleDayNightMode()` in `themes.ts`; `index.ts`'s `toggleDayNightModeAndTrack()` wraps it for achievement tracking
- **Font-size zoom:** `applyAppZoom()` in `src/renderer/settings.ts`
- **Dock drag-reorder/collapse:** `createDockManager()` in `src/renderer/docks.ts` — a factory (originally hardcoded to the right-sidebar power-tool docks, generalized this session) that takes a container element + its own localStorage keys + a default order and returns `{init, reset}`; each instance's sections reorder/collapse only relative to each other, never across instances. The original right-sidebar docks (Tag Pruner/Unify-Void, `initDockSystem()`/`resetDockLayout()`) and SynthDat Overseer's left column (`initSynthDatSectionDocks()`, called from `synthdat-overseer.ts`'s init — ONLY the settings column, `#synthDatCol1`; Prompt fields and the full-width Generation section at the top are deliberately excluded since they're worked in constantly) are two separate instances of the same factory, not copies of the logic.
- **Shrink-text-to-fit for compact controls (dropdown buttons):** `shrinkTextToFit()` in `shared-ui.ts` — reduces an element's own `font-size` (inline style) until its content fits its box, instead of losing characters to `text-overflow: ellipsis` (still kept as a safety net for whatever's left over at the font-size floor). Wired into every `buildPersistentDropdown()`-built button's label-set path and `initThemeDropdown()`'s (themes.ts) separate near-duplicate implementation — both call it after every `textContent` change, including the initial one (must run after the element is actually in the DOM, since `clientWidth` is 0 before layout).
- **Hover tooltips (custom, not native `title`):** the `mouseover`/`mouseout` pair in `index.ts` near `tooltipBubble` — strips the native `title` attribute and shows a themed bubble after `tooltipDelayMs`, with two extra behaviors: `placeholderOverflowWidth()` also triggers the bubble for an empty field whose placeholder is visibly cut off (canvas-measured, see Known Pitfalls — `scrollWidth` doesn't work for this), and `showTooltipBubble()` pins the bubble to the bottom of the screen (with an accent-glow highlight, `.tooltip-bottom-pinned` in styles.css) instead of placing it just below the trigger whenever there's no room above — the normal case for topbar buttons, where an adjacent-below tooltip can end up hidden under the cursor at small font sizes or with a custom cursor.

- **Tag mutation (add/remove/undo-redo/disable-restore/save):** `src/renderer/tags-edit.ts`
- **Retroactive Merge/Void (standing merge/void rules, gallery right sidebar dock):** `src/renderer/canonical-tags.ts` — see its own Feature Overview entry and header comment
- **Quick Merge / bulk operations:** `src/renderer/quick-merge.ts`, `src/renderer/master-tag-control.ts`

## Feature Overview

**Core editing:** add/remove tags, full undo/redo with per-entry revert, Danbooru wiki definitions, tag autocomplete against `all_tags.json`, filter (AND/OR/XOR/NOT), sort by family/frequency/alpha, 3-dot image menu (text/language, comic/koma, review flags, blur, notes).

**Views:** Grid (modal, zoom/pan), Compact (shift+click sticky comparison), Single (multi-image tag-alignment table).

**Power tools:** Master Tags (checkbox-driven conditional apply/remove/find-replace), Tag Pruner (merge/void picker), Unify/Void (merge/delete, optionally including disabled images), Retroactive Merge/Void (standing rules, see below).

**Dock system:** drag-reorder (dropping onto another dock swaps them regardless of cursor position within it), collapse/expand (animated open/close), resize; docks are Tag Pruner, Unify/Void, Retroactive Merge/Void, Quick Merge; Settings has a reset-layout option.

**Retroactive Merge/Void:** a dock in the Gallery's right sidebar (`src/renderer/canonical-tags.ts`) holding standing rules of the shape `[child tag, child tag, ...] → canonical tag` (merge) or `[child tag, ...] → ` empty/void (delete outright, no replacement — represented as a rule with `canonical: null`, not a separate mechanism). Persisted per-dataset as `_dts_canonical_tags.json`; on first load of a dataset with no such file yet, rules are reconstructed once from that dataset's `_tag_edit_log.json` merge/void history, then that reconstruction is never re-run (the persisted file becomes the sole source of truth, so a user can freely edit/delete a rule without it reappearing from log history). Every rule is applied to every GALLERY entry (Disabled and Unsaved Approved are out of scope — see below) via `applyCanonicalRules(entry)`, hooked directly into `tags-edit.ts`'s `markDirty()` — the one funnel every tag-mutating path in the app already calls (Quick Merge, Tag Pruner Unify/Void, WD14, undo/redo) — so a child tag is auto-corrected "by any means" the instant it lands on any loaded Gallery entry. Adding or editing a rule (via the dock directly, or automatically whenever Tag Pruner's own Unify/Void actions run) also triggers `resweepAllEntries()`, which re-applies every current rule to every currently loaded GALLERY entry (skipping locked entries, per the usual mass-tool convention) — this is what makes it retroactive: an image that missed a merge/void gets caught up the moment the rule exists, with no separate manual replay step.

**Full control over what is and isn't subject to a rule, at three levels:**
1. **Per-rule:** each rule has an `enabled` checkbox in the dock — pausing it stops it from applying anywhere without deleting it or forgetting its children; re-enabling immediately resweeps.
2. **Per-child-tag:** each child tag chip has its own checkbox (separate from the × delete button) — unchecking excludes just that one tag from the rule's effect while keeping it on record (e.g. merged "black dress"/"frilly dress"/"dress" into "black frilly dress" but want to stop folding in plain "dress" without forgetting it was ever part of the rule).
3. **Per-image:** `entry.meta.mergeImmune` and `entry.meta.antivoid` (independent booleans) permanently exempt one image from every merge rule and/or every void rule respectively, regardless of the dock's own settings — a stronger, always-on version of Lock (which only skips *mass tools in general*, not this specific mechanism, and isn't permanent in the same sense). Toggled via `view.ts`'s 3-dot menu (per-image) or `master-tag-control.ts`'s Tag Overseer mass-select buttons (`setEntryFlagsForSelection()`) — both surfaces also offer "Antimmunize" as a one-click shortcut that sets/clears both flags together, not a third independent flag.

**Turning a rule (or one child of it) off actively unmerges/unvoids, using the edit log as the source of truth for exactly what to restore — not just "stop future correction."** `canonical-tags.ts`'s `unmergeChildren(rule, childrenBeingTurnedOff)` builds a one-time index from `editLog`'s own `{mergedTags/voidedTags, affected: [{base, prevTags, newTags}]}` records (already written by every merge/void action, see `recordChange()` in `tags-edit.ts`) mapping each child tag to the exact set of image bases that log proves genuinely had that tag before it was folded/removed. Per Gallery entry with the canonical tag present: any child being turned off that the log proves this SPECIFIC image had gets added back; the canonical tag itself is only dropped once no other still-active child of the rule is proven present on that image either — so an image that only ever had "dress" (merged into "black frilly dress" alongside images that had "black dress"/"frilly dress" too) gets exactly "dress" back and loses the canonical tag, while an image that had both "black dress" and "dress" keeps the canonical tag (still justified by "black dress") and additionally gets "dress" back alongside it. Void rules restore independently per child (no canonical to reconsider). This runs from: the per-rule "Enabled" checkbox going off, a per-child chip checkbox going off, that chip's × (forget entirely), and the rule's own 🗑 Delete button — all four treat "which children to restore" as everything being turned off in that action, evaluated against the rule's FINAL state (so a whole-rule disable, which turns off every child at once, correctly drops the canonical everywhere it's no longer justified rather than only checking one child at a time). Turning a rule/child back ON needs no mirrored "re-merge" call — the existing `resweepAllEntries()` naturally re-folds it forward. The restoration itself is logged as its own `'unmerge'`/`'unvoid'` entry (one per action, covering however many images it touched — so voiding, unvoiding, then voiding the same tag again shows as three separate, correctly time-ordered log rows, not one entry mutated in place) via the same `recordChange()` mechanism `'merge'`/`'void'` use, giving it Undo/Redo buttons in the Log panel too. The rule CONFIG change itself (pausing/resuming, adding/removing/toggling a child, creating, deleting) is logged separately as a `'rule-update'` entry via plain `pushLogEntry()` — no `affected` tag data, so no Undo/Redo button for it, just a record of what changed and when.

**A rule's canonical tag is allowed to also appear in its own children list** (e.g. merging "black dress"/"dress" into canonical "black dress" itself, to formally record that "black dress" is part of the merge group) — `applyCanonicalRules()` handles this as a no-op for that exact tag (filtered out, then always re-added), and typing the canonical tag by hand is never treated as "blocked by its own rule" (see below).

**Typing a tag by hand that's an active child of an applicable rule is BLOCKED outright, not silently rewritten** — `tags-edit.ts`'s `addTagToEntry()` (the universal manual single-tag-add path: chip input, autocomplete, WD14 review, the language/comic/koma checkboxes) calls `canonical-tags.ts`'s `findBlockingRule(tag, entry)` first; if it returns a rule, the add is refused with a toast ("This tag is affected by a merge/void rule; please check the dock area for details.") instead of adding-then-correcting. This does NOT apply to automatic/bulk paths (Quick Merge, Master Tags mass-apply, WD14 bulk) — those still add-then-let-`markDirty()`-correct as before, since blocking would silently drop tags from an unattended batch operation with no way for the user to notice.

Replaces two older, narrower things (both removed): `tags-edit.ts`'s checkbox-driven `retroApplyToDisabled()`/`retroApplyAllToDisabled()` (only caught up Disabled images if the user remembered to click a replay button, with no visibility into what rules existed), and `synthdat-overseer.ts`'s own independent `buildMergeHistoryMap()` (now reads from this module's shared `canonicalRules` instead of its own separate editLog-diffing reconstruction).

**UI animation mode** (Settings ▸ Layout & Panels, `dts-ui-animation-mode`): Fade (default) / Swipe / Off. Drives every menu/dropdown/flyout pop-in, floating panel open/close, tab switch, gallery view switch, single-mode prev/next, and the image modal — all read timing from shared CSS vars (`--pop-dur`/`--panel-dur`/`--tab-dur`) that Off zeroes out, and check `html.motion-swipe` to pick a directional slide over the default fade/scale. Swipe direction is fixed per pane where it's unambiguous (Datasets ← left since it's the leftmost tab, Editing Stats/Tag Overseer's right-sidebar takeover ← right) and computed per-transition for gallery views/single-mode paging (left-of/right-of the previous one in view/image order). The image modal becomes a bottom-sheet slide-up instead of a scale-in under Swipe. See `mem:conventions` for the mechanism.

**Distribution:** portable build, no AppData dependency; updates are a fresh zip download + moving `data/` over (no in-app updater); GitHub package generator for source-only export.

**Other:** 25 themes (4 free + 21 shop, common→legendary, 40–750 Edibits) each with `--accent-flair` + a distinct flourish, epic/legendary get the hover-fill button effect — any other theme can individually buy that same effect via the Shop's 🔨 Refine Theme button (cost = epic price minus that theme's own price), toggleable off via Settings' "Suppress Theme Upgrade"; 45+ achievements with rarity tiers; night/day mode; font-size zoom (1.4x–3x); custom fonts; power-tool card highlighting; empty-state random-fact button.

**Dataset tab:** the app's tabs are Datasets / Gallery / 🏷 Tag Overseer / Editing Stats (the tag editor itself is "Gallery" — "Datasets" is a separate folder manager). Datasets shows every dataset folder ever opened as a themed folder icon (grid or list), sortable manually (drag) or by filename/time-opened/time-added, with a right-click/3-dot context menu per folder (remove, pin as favorite — syncs into the separate ★ Favorites store — view that folder's achievements read-only, change the icon to a generic outline or a picked in-folder image). Opening any not-yet-tracked folder (via File ▸ Open, or the tab's own dashed "+" tile) prompts once to add it to this tab; answering No suppresses that prompt permanently (the "+" tile always adds regardless, with no prompt). Switching the active dataset by any of these means (or Favorites) prompts to save unsaved edits first, same as Quit/Restart/Unload.

**WD14 Autotagger:** Tag Overseer's "🐍 WD14 Autotagger" section sends selected image(s) (or a single image via its 3-dot menu entry) to a WD14 Tagger node on a user-run ComfyUI instance (default `http://127.0.0.1:8188`) and merges the returned tags onto each card. Settings (host, model — scraped live from ComfyUI, threshold, character threshold, replace-underscore, trailing comma, exclude tags) live entirely in that one expandable section. "Apply tags automatically" toggles between committing immediately and a review modal (per-image editable tag list, checkbox to skip) before anything is written; either way the whole batch commits as one undoable `add-tag` edit-log entry. The app holds no model itself — ComfyUI does all the inference.

**Hardware acceleration** (Settings ▸ Performance, `hwAccelToggle`): on by default, in which case this app's own UI rendering is steered onto the machine's INTEGRATED GPU rather than a discrete one (still hardware-accelerated, just on the weaker adapter) — added after measuring a real ~30% discrete-GPU load from this app's own compositing alone, directly competing with ComfyUI's actual inference use of that same GPU. Turning it off disables GPU acceleration entirely (pure software/CPU rendering) for anyone who'd rather have zero GPU usage, or who has a GPU they don't mind this app using and wants max smoothness on their own hardware instead of being steered to the integrated one. Windows-only mechanism; whichever choice is made can only take effect at the next launch (Chromium/WebView2 decide their GPU path once, at startup, before any window exists), so the toggle just persists the choice to a small file the main process reads directly (not the renderer's localStorage — unreachable that early) and prompts a restart. See Known Pitfalls for the two-mechanism implementation (a Chromium switch, plus the actual OS-level fix: writing this app's own per-exe entry into `HKCU\Software\Microsoft\DirectX\UserGpuPreferences`, the same registry key Windows' own Settings ▸ Display ▸ Graphics panel writes).

**SynthDat Overseer:** a dedicated tab that drives a user's own ComfyUI instance to generate synthetic dataset images — the actual use case: train a rough character LoRA on a thin dataset, then generate MORE images of that character strong-armed into arbitrary reference poses via ControlNet (Anima-LLLite), to grow the dataset. This is built around exactly ONE fixed, hand-authored ComfyUI workflow (not a generic "load any workflow" system) — see Critical Constraints for the node-id map. Flow: pick a reference pose image → WD14-interrogate it (reuses the WD14 Autotagger bridge) → hand-assign each returned tag to Pose/Limbs/Sexual/skip in a per-tag picker (pre-suggested from Danbooru's own posture/gestures/hands/feet/shoulders tag-group wiki pages, but never auto-applied — picking a new reference image does NOT clear or re-interrogate anything by itself; the user re-interrogates and re-applies manually, or uses the tag-migration picker's own Clear-vs-Compound choice) → fill in the rest of the prompt fields (Global/Character/.../Negative) → Generate (1-Pass by default, optional 2nd-pass refinement pass, live TAESD preview + Stop button via a WebSocket opened in `main.ts` — when 2-Pass is enabled, BOTH the pass-1 and pass-2 results come back from the same run and a small picker lets the user choose which one to keep, defaulting to the refined pass-2 result, before Accept/Reject; see Critical Constraints' node-id map for the `192_pass1` node this relies on) → a final editable tag-chip card (reuses `.chip`/`.chiprow`) shows exactly what will be saved, with per-tag prune, a "this dataset already merged this tag into X elsewhere" suggestion reconstructed from `editLog`, and a "🐍 Re-interrogate output with WD14" button that runs WD14 on the actual generated image (not the reference) — the model sometimes draws details nobody prompted for (e.g. adds lily pads to a pond on its own), and this is the same WD14 bridge, just pointed at the output instead of the reference (`reinterrogateOutput()`). A checkbox picks Compound (default — only ADDS tags not already in the list, by normalized comparison; existing prune/merge decisions on tags already there are untouched) vs Overwrite (replaces the whole tag list with WD14's output tags, discarding prior prune/merge decisions too since there's nothing left for them to apply to) → Accept stages the image+tags in the dataset's `Unsaved Approved/` folder as a normal unsaved edit (appended live into `entries`, no reload — see Data Flow's "Unsaved Approved" entry for the full save/promote lifecycle) rather than writing straight into the root; Reject (and any pass not chosen by the Pass 1/2 picker) writes immediately and hands it to `tags-edit.ts`'s `moveEntry(entry, true)` so it lands in `Disabled/` like any other disabled image instead of a separate "rejects" folder — see Data Flow's "SynthDat Accept/Reject pass-choice semantics" for exactly what happens to each pass. ControlNet itself is optional, not mandatory — "I don't want to use a reference image (skip ControlNet)" bypasses the reference image, LoadImage, Image Resize, and ControlNet nodes entirely for an ordinary prompted generation (see Critical Constraints' node-id map for exactly which nodes get deleted). Has its own independent ComfyUI host setting (`synthDatHost`, not shared with Tag Overseer's WD14 host) and its own persisted settings blob (`dts-synthdat-settings`, survives dataset unload/app restart — Pose is deliberately excluded since it's tied to a specific reference image/session, not the character's standing description). **Layout:** a full-width Generation section (`.synthdat-gen-top` — seeds, Generate/Stop, live preview, pass picker, output preview, re-interrogate, tag card, Accept/Reject) sits above a two-column row (`.synthdat-cols`): left is the settings column (`#synthDatCol1`, collapsible/reorderable — see Dock drag-reorder/collapse above), right is Prompt fields. The reference image and its padded/resized preview sit side by side (`.synthdat-refs-row`), not stacked. Every preview image in this tab (reference, resized/padded, live TAESD, pass 1/2 thumbnails, final output) opens the same `showImageLightbox()` (shared-ui.ts) on click, which also supports scroll-wheel zoom past its normal fit-to-screen size (clamped 1x–6x) plus drag-to-pan once zoomed in — that's a shared, app-wide capability, not SynthDat-specific. Panning only engages past 1x scale, and a `didDrag` flag distinguishes an actual drag from a plain click (mouseup after dragging still fires a native `click` on the same target, which would otherwise close the lightbox the instant you finish panning).

## Known Pitfalls (read before touching related areas)

- **Wrapping a `.tool-section`'s children in a plain `<div>` (e.g. to gray out a sub-area as one unit) silently breaks that section's spacing for everything now one level deeper.** `.tool-section` gets its rhythm from `display:flex; flex-direction:column; gap:10px` on ITSELF — that only spaces its own DIRECT children. `#synthDatRefImageSection` (index.html, added so "skip reference image" could gray out the whole reference-picker sub-area via one class toggle) is a bare div with no layout of its own; everything inside it collapsed together with zero spacing (two buttons even rendered side-by-side instead of stacked) since they're no longer direct children of the flex container. Fixed by giving the wrapper the same `display:flex; flex-direction:column; gap:10px` as `.tool-section` itself. Any future "wrap part of a tool-section to toggle it as a unit" needs this same treatment, not just the wrapping div.
- **After reparenting a popup to `document.body`, every OTHER "is this click outside my own bounds" check in the app that used to work via plain DOM containment now has a blind spot.** A floating panel's own outside-click-to-close logic (`getOutsideClosablePanels()`'s consumer in index.ts) checks `!panel.contains(ev.target)` — that was reliable when a `.pdrop-menu` opened from a button inside the panel was ALSO a DOM descendant of it, but once it's reparented to `document.body` (see the pitfall below), a click on one of ITS OWN dropdown's items no longer satisfies `panel.contains(...)` at all, so the panel treats picking an option in its own dropdown as an outside click and closes itself — before the dropdown item's own click handler (and whatever toggle/logic it guards, e.g. "close after picking an option") ever runs. Symptom looked exactly like "the close-on-select preference is being ignored," but the preference code never even executed — confirmed by adding a `console.error` directly in the item's click handler and seeing it never fire. Fixed with `isClickInsideOwnedPdrop(panelEl, target)` (shared-ui.ts) — tracks the currently-open pdrop-menu's element alongside its owner panel, and the panel's outside-click check now also passes if the click landed in a pdrop-menu that panel itself owns. Any future "is this click inside/outside X" check needs the same treatment if X can contain a reparented-to-body popup.
- **You cannot "swallow" a click by calling `stopPropagation()`/`preventDefault()` on its preceding `mousedown` — they're two separate event dispatches, and by the time any bubble-phase `click` listener notices something just closed, the click has already reached its target and fired that target's own handlers.** Settings' "swallow the click that closes a menu/panel" toggle (`outsideClickSwallowToggle`, `shouldSwallowOutsideClick()`/`markSwallowNextClick()` in shared-ui.ts) needs the decision made and enforced in the CAPTURE phase, before target-phase — floating panels and pdrop-menus (whose own outside-click-close already fires on `'click'`) do this directly, in the same capture-phase listener that decides to close (`ev.stopPropagation(); ev.preventDefault();` right there). header-cat-flyout is the exception: its outside-click-close deliberately fires on `'mousedown'`, not `'click'` (a separate hard-won fix, see the pitfall below — do not change that trigger), so its mousedown handler can't decide-and-swallow the click in the same event; it calls `markSwallowNextClick()` instead, and a single shared capture-phase `'click'` listener consumes that mark on the very next click. Any future "outside click closes X" feature needs this same capture-phase-and-immediate-stop shape to support swallowing, not a bubble-phase listener.
- **Reparenting a popup to `document.body` to escape an ancestor's `overflow`/z-index decouples its lifecycle from that ancestor — closing the ancestor no longer implicitly hides a DOM descendant that isn't one anymore.** `.pdrop-menu` (`buildPersistentDropdown()`, shared-ui.ts) was moved from living inside its own small `.pdrop` container to `document.body` with `position:fixed` so it could no longer be clipped by a scrollable/overflow:hidden panel (e.g. Settings) it happened to open from — but this left an orphaned, still-visible dropdown floating on screen after the Settings panel itself closed, since the menu was never actually a child of that panel to begin with once reparented. Fixed with a small shared registry (`openPdropClose`/`openPdropOwnerPanel` in shared-ui.ts): `hidePanel()` closes the currently-tracked pdrop-menu if (and only if) it belongs to the panel being hidden, and opening any pdrop-menu or floating panel closes every OTHER one first (`closeAllFloatingPanels()`) — general mutual exclusion, not just this one pair. Also needed a z-index bump (`.pdrop-menu` to 460, matching `.ctx-menu`) since it can open from a button living inside a `.theme-panel` (z-index 455) and must render in front of it, not behind. Any future "move this popup to body to fix clipping" fix needs the same tracking, not just the reparent.
- **A shared CSS class used for one visual purpose (width/max-height) can carry an unrelated one (centering) that silently applies somewhere it shouldn't.** `#settingsPanel` has class `theme-panel log-panel` — `.log-panel` exists to give Log/Achievements a wider, `left:50%; transform:translateX(-50%)`-centered layout, but Settings inherited that centering too, with no way to tell from Settings' own markup why it wasn't anchored to the ⚙ button that opened it. Fixed with an `#settingsPanel`-specific override (`left:auto; right:auto`, no translateX) plus real anchoring: `btnSettings`'s click handler now positions it via `positionMenu()` (same viewport-clamped helper every dropdown/context-menu uses) from `btnSettings.getBoundingClientRect()`, called AFTER `showPanel()` so `offsetWidth` is measurable (a `display:none` element reports 0). When a panel/menu "looks centered for no reason," grep for which shared class is actually responsible before assuming it's that element's own rule.
- **Inline styles always beat stylesheet rules, regardless of CSS specificity.** If "the CSS looks right but isn't applying," grep for a `.style.X =` assignment in JS before doubting the stylesheet.
- **A synthetic/isolated repro can pass while the real app fails**, if the real bug lives in unrelated code that only runs on the real end-to-end path. When a fix looks right in isolation but is reported still broken, inspect the real live failing state (devtools) instead of refining the repro.
- **When a bug traces to a shared CSS class, check every element using that class, not just the one reported.** `.theme-panel` backs 7 different floating panels.
- **`overflow: hidden` on a flex child resets its `min-height` to `auto`→`0` per spec**, letting flexbox squeeze it below its content height even when the parent has room to scroll. Fix with `flex-shrink: 0` on that child, not by removing the needed `overflow: hidden`.
- **A flex item's default `min-width: auto` means it can't shrink below its own content's width.** If a flex row contains a `white-space: nowrap` button/label, that item can't shrink below its full label width and can overflow the row at larger zoom/font sizes. Fix with `min-width: 0` + `overflow:hidden; text-overflow:ellipsis` + `flex-grow: 0` on the ONE item that's the actual problem, `flex-shrink: 0` on items that must never shrink. Don't apply `min-width: 0` defensively to neighbors — it lets them collapse to a 0px box with invisible overflowing text instead of clipping visibly.
- **Never trust a build tool's side effects without testing them directly.** `electron-builder --dir` fully wipes and regenerates its whole output dir on every build.
- **Confirm a background process has actually exited (`tasklist`) before trusting its output artifact's size/contents.**
- **An ES module import is a live but read-only binding** — the importer can mutate its contents (`.push()`, `obj.field = x`) but `importedName = newValue` throws. Any module-owned state another file needs to *reassign* must go through an exported reset function, never a raw mutable export reassigned from outside.
- **A clean `npm run build` does not prove every reference resolves** — esbuild validates named ES-module imports have a matching export, but a bare undeclared-global reference (a symbol that moved to another module and was never re-imported) is invisible to it and only throws at runtime when that code path executes. After any module-boundary change, grep for the moved symbol's old call sites and re-check each `init(deps)` object against what that module actually uses.
- **`index.ts` is one big top-level IIFE — a single uncaught `ReferenceError` anywhere in it silently disables every statement after it**, with no error dialog and no visible symptom beyond "these buttons just don't do anything." Electron doesn't forward renderer console output to the terminal by default — to catch a silent renderer exception fast, launch the packaged exe as `ELECTRON_ENABLE_LOGGING=1 "./Dataset Tag Studio.exe" --enable-logging=stderr` and grep captured stderr for "Uncaught". Do this after any module-boundary change, not just a full click-through.
- **A native `<select>`'s own dropdown popup is OS-rendered and outside JS's control** — Chromium/Electron dismisses it the instant the mouse wheel scrolls anywhere outside it, with no click/blur/scroll event JS ever sees to intercept. If a future bug report says a dropdown/list "closes on scroll," check whether it's backed by a native `<select>` first; if so, no amount of outside-click-listener tuning will fix it — only replacing the visible control with a fully custom one will (see `initThemeDropdown()` in `themes.ts` for the pattern: keep the native `<select>` hidden as the value store, drive it from a custom `.pdrop`-style `<div>` with no scroll listener at all).
- **Never render another folder's achievements through the live `folderStats`/`folderUnlocked` globals in `achievements.ts`.** Those represent whichever folder is actually open right now; mutating or reassigning them to peek at a different folder's stats (e.g. from the Dataset tab's "View achievements" on a folder that isn't currently open) would corrupt the real session's in-memory state. Instead read that folder's `_dts_achievements.json` directly off its own stored `FileSystemDirectoryHandle` and pass the parsed `unlocked` array into `renderAchievementsPanel(unlockedOverride)` — it accepts an optional override for exactly this, defaulting to the live global when called with no args (see `dataset-manager.ts`'s `openReadOnlyAchievements()`).
- **`electron-builder` REWRITES `package.json` for every packaged build — it strips `scripts`, `devDependencies`, and `build`, unconditionally, and this isn't configurable.** Confirmed by diffing the real project `package.json` against the copy sitting inside a built `app.asar` (via `asar list`/`asar extract`). Any feature that reads `package.json` off disk at runtime (the "Generate GitHub package" export did) gets this stripped copy in every packaged/portable/shipped build, never the real one — even though it looks identical in an unpackaged dev run, where `package.json` is the real file. Anything that needs the real scripts/devDependencies/build config at runtime has to carry its own copy as a source-embedded constant (see `GITHUB_PACKAGE_SCRIPTS`/`_DEV_DEPENDENCIES`/`_BUILD_CONFIG` in `main.ts`) and merge it with whatever's actually on disk, not read those three fields from disk directly.
- **`electron-builder`'s `build.files` whitelist silently drops every `**/*.d.ts` file, and an explicit include entry for that exact path does NOT override it** (tested directly: adding `"src/renderer/global.d.ts"` as its own `files` entry still produced no `global.d.ts` in the packaged `app.asar`). If a `.d.ts` file needs to ship inside a packaged build for any reason (ours did, for the GitHub package export to be typecheckable), rename it to a plain `.ts` file instead of fighting this — a `declare global {}` block works identically regardless of extension. See `global-types.ts`.
- **A drag-reorder that always "inserts before the drop target" is direction-asymmetric — dragging an item down its own list only ever moves it one slot short of where it was dropped, while dragging up works perfectly.** Removing the dragged item from the array shifts every later index left by one; if the target was originally AFTER the dragged item, "insert before target" lands one short of the drop point (dropping onto the very next item does nothing at all). If the target was originally BEFORE it, nothing shifts, so "insert before" lands exactly right — which is why only the "drag down" direction ever felt broken. Fix (used in both `tag-index.ts`'s family reorder and `docks.ts`'s `reorderDock()`): insert AFTER the target instead, whenever the dragged item's original index was less than the target's. Apply this to any future drag-reorder list, not just these two.
- **A CSS transition driven by inline styles must reset EVERY property it touched back to its resting value once the transition ends, not just the ones a "final state" function already cares about.** `docks.ts`'s animated dock collapse set `max-height`/`opacity` on each collapsible row to drive the animation, but only ever reset `transition`/`overflow` afterward — `max-height` stayed permanently pinned at whatever `scrollHeight` happened to be measured mid-animation, on every row, forever (confirmed live via Chrome DevTools Protocol: `remote-debugging-port` + a raw CDP websocket driven from Node, clicking the real collapse button and reading `el.style.maxHeight` after the transition — it never went back to `''`). Reproduce a "some element's layout looks subtly wrong and won't reset" report this way (attach CDP, click the real control, read the actual computed/inline styles) rather than guessing from source alone; the wrong value here didn't show up as an error, an obviously broken layout in every test, or anything the build/launch pitfalls above catch.
- **A bare reference to an element's own `id` can silently work without ever importing it from `dom.ts`** — any element with an `id` attribute is automatically exposed as a same-named global on `window` per the HTML spec's "named access on the Window object," so `someElementId.addEventListener(...)` in `index.ts` can run correctly for months with no import at all, entirely by accident. Caught only by noticing the name genuinely wasn't in the destructured `from './dom'` import list, despite the code working and no console error ever appearing (it's not a `ReferenceError` — the implicit global resolves it). Always import element refs from `dom.ts` explicitly, even when a quick manual test says the bare name "works."
- **An empty `<input>`'s `scrollWidth` does not reliably reflect its placeholder text's rendered width** — Chromium computes `scrollWidth` from actual value content, and there isn't any when the field is empty, so `el.scrollWidth > el.clientWidth` can stay `false` even when the placeholder is visibly cut off. To detect placeholder overflow (used for the hover-tooltip-shows-full-placeholder feature, `index.ts`'s `placeholderOverflowWidth()`), measure the placeholder string directly via a throwaway `canvas.getContext('2d')` + the field's own computed font (`measureText().width`) instead — the standard reliable way to measure text width without relying on DOM overflow metrics.
- **A renderer-side `fetch()` to a local server (e.g. ComfyUI) can silently fail even when that server is running fine** — verified live against ComfyUI's own `server.py`: without `--enable-cors-header` it runs an `origin_only_middleware` that 403s cross-origin POSTs, and separately Chromium enforces normal CORS on the response either way. Neither check applies to a plain Node HTTP client. Any "talk to a local HTTP server" feature belongs in `main.ts` (IPC handler using Node's `http`/`https`), not a renderer-side `fetch()` — see the WD14 Autotagger's `wd14-get-models`/`wd14-tag-image` handlers for the pattern (manual multipart body for the upload, since no form-data dependency was added).
- **A GPU/hardware-acceleration preference can only be decided once, before `app.whenReady()`/any window creation — never mid-session.** Chromium/WebView2 pick their GPU process and adapter at startup; there is no live "switch GPUs now" API. Any such preference (`hardwareAccelToggle`) has to live in its own small file the main/Rust process reads directly at the very top of startup, NOT the renderer's `localStorage` (unreachable before any window/webview exists) — the Settings toggle just persists a choice there and prompts a restart, same shape as the close-confirm guard's own startup-only constraints.
- **A Chromium command-line switch (`--force_low_power_gpu`) alone is not the reliable way to steer a hybrid-graphics laptop onto its integrated GPU — the actual OS-level mechanism is a registry key.** Confirmed by building this both ways: the switch only affects Chromium's own internal adapter choice, while writing this app's own full exe path into `HKCU\Software\Microsoft\DirectX\UserGpuPreferences` (value `GpuPreference=1;`, `REG_SZ`) is literally what Windows' own Settings ▸ Display ▸ Graphics panel does when a user manually sets an app to "Power saving," and steers DXGI's adapter enumeration before Chromium/WebView2 even starts. Use both together (the registry key is the one that actually matters; the switch is free insurance) — see `main.ts`'s `preferIntegratedGpu()` (shells out to `reg.exe add`/`query`, no dependency needed). Gate the registry write to release/packaged builds only — in dev, `app.getPath('exe')` points at a shared or per-project debug binary, not the thing a real user will actually run.
- **A locked image (`entry.meta.locked`) must be skipped by every mass/automatic tag operation, but NOT by manual single-image actions.** Toggled via the 3-dot image menu (`view.ts`'s `openImageOptionsMenu` — shared by Grid and Single view, so one toggle covers both), plus mass lock/unlock in Master Tags (select images, then Lock/Unlock selected) and a toolbar "🔓 Unlock all" button next to the Single view toggle. "Automatic tool" means: Quick Merge (`quick-merge.ts`), Unify/Void and the retroactive disabled-image catch-up (`tags-edit.ts`), every Master Tags mass/conditional/rename/find-replace action AND its Apply/Remove-to-Selected buttons (`master-tag-control.ts`), and the bulk WD14 trigger (`wd14-tagger.ts`'s `runBatch`, filtered before it starts — its single-image 3-dot trigger is intentionally exempt, since that's a manual action naming one specific image). Any FUTURE feature that loops over `getEntries()`/`filteredEntries()` and mutates tags without the user hand-picking that exact image in the moment must add `|| e.meta.locked` (or `&& !e.meta.locked`) to its skip condition, matching the existing `e.disabled` checks right next to it in each of those files.
- **`markDirty(entry)` (`tags-edit.ts`) is the universal tag-mutation funnel — every tag-mutating path in the app calls it immediately after mutating `entry.tags`, even ones that bypass `addTagToEntry`/`removeTagFromEntry` by reassigning `e.tags` directly** (Quick Merge, Tag Pruner Unify/Void, undo/redo, WD14). Confirmed by grepping every call site before relying on it. Any future feature needing to react to "a tag changed, by whatever means" belongs hooked into `markDirty()` itself, not threaded into each individual mutation site — see `canonical-tags.ts`'s `applyCanonicalRules(entry)` call at the top of `markDirty()` for the pattern.
- **Retroactive Merge/Void's scope was deliberately narrowed to Gallery-only, reversing its own original design from earlier in the same overall feature's development.** The dock originally reswept Disabled images too ("It should autosweep all existing once added since it is retroactive" was the explicit instruction that shaped that first version). A later round of the same feature explicitly asked for the opposite: rules and the Merge Immunize/Antivoid exemptions should only affect Gallery-visible entries, with Disabled/Unsaved Approved entries frozen exactly as-is until restored. `applyCanonicalRules()` now returns `false` immediately for `entry.disabled || entry.pendingApproval`, and `resweepAllEntries()` skips them before even calling it. Don't "fix" this back toward sweeping Disabled images by pattern-matching the word "retroactive" against the dock's name — re-read this entry and `canonical-tags.ts`'s own header comment first; the scope was a deliberate, confirmed decision, not an oversight.
- **Every log-panel entry type used by `edit-log.ts`'s `TAG_TYPES`/`STAT_CHART_COLORS`/`STAT_TYPE_LABEL` maps must be added to ALL THREE, or it silently renders with no Undo/Redo buttons and/or an unstyled/unlabeled Stats-tab slice.** `'unmerge'`/`'unvoid'` (canonical-tags.ts's `unmergeChildren()`, logged via the injected `recordChange` dep the same way `'merge'`/`'void'` already are) and `'rule-update'` (pure rule-config changes — pause/resume, add/remove/toggle a child, create, delete — logged via a plain `pushLogEntry()` since there's no tag-level `affected` data for Undo/Redo to act on, so `'rule-update'` is deliberately NOT in `TAG_TYPES`) were added this way. When adding a new log entry type anywhere, check whether it belongs in `TAG_TYPES` (real `affected: [{base,prevTags,newTags}]` worth an Undo/Redo button) before wiring it in.
- **The 3-dot image-options menu (`view.ts`'s `openImageOptionsMenu()`) keeps each button's visible label to just the action name — the full explanation goes in `title` (hover tooltip), not the label.** It had grown to read as a wall of text once Merge Immunize/Antivoid/Antimmunize joined Disable/Lock/Reset/WD14 with full-sentence labels. Any new item added to this menu should follow the same shape: short `textContent` (icon + 1-3 words), the explanation in `title`.
- **A per-image flag can be "locked-like" without being Lock.** `entry.meta.locked` (skip mass tools) and `entry.meta.mergeImmune`/`.antivoid` (permanently exempt from merge/void rules specifically) look similar (both are `entry.meta` booleans toggled from the same 3-dot menu) but answer different questions — Lock is "don't let an unattended batch operation touch this image at all," while Merge Immunize/Antivoid is "this specific image should never get corrected by the standing rules, even when I deliberately re-trigger them." An image can be immune to merges but still be affected by Master Tags' mass-apply, for instance. Keep them as separate flags, not variants of one "protected" concept, if a future feature wants to add a third such exemption.
- **"Tag X was merged into tag Y" now has one shared source of truth app-wide: `canonicalRules` (`canonical-tags.ts`), not a per-feature reconstruction.** SynthDat Overseer's tag-card merge suggestion (`buildMergeHistoryMap()`) originally diffed `editLog`'s own `{prevTags, newTags}` pairs independently to reconstruct this; it was refactored this session to instead read the same shared `canonicalRules` the Retroactive Merge/Void dock maintains, since maintaining two separate reconstructions of the same fact is exactly the kind of stale-duplicate-system drift to avoid. Any future "was this tag ever merged/superseded" need should read `canonicalRules` directly, not add a third reconstruction.
- **Setting a textarea's `style.height` via JS (for auto-grow) silently defeats its `rows` HTML attribute for EMPTY content, even though `rows` alone would size it fine.** `scrollHeight` for an empty `<textarea>` collapses to roughly one line the moment any inline `height` has been set (even `height:auto` first, to remeasure), regardless of what `rows` says — so a "grow to fit on load" pass that runs unconditionally over every field (including ones with no saved content yet) visually shrinks them below their own HTML default. Fix is a CSS `min-height` floor (SynthDat Overseer's prompt fields use `min-height: 52px`), not touching the JS — `min-height` still wins over a smaller inline `height` regardless of how that height was computed.
- **The "Generate GitHub package" feature (`main.ts`'s `copyGithubPackageSource()`) used to copy `main.js`/`preload.js` verbatim from disk into the exported package, alongside the real `src/` it also ships** — contradicting its own stated intent ("ships source, not a compiled copy") and risking a genuinely stale compiled copy if the exporter had edited `src/` without rebuilding first. Harmless in practice (any real workflow from the export runs `npm run build` as a `pre*` step before it matters) but confusing, and neither the exported `GITHUB_GITIGNORE` nor this project's own `.gitignore` excluded those generated files — so they could get committed as tracked build output into what's supposed to be a clean-source GitHub repo. Fixed by dropping them from the copy list (matching `renderer/app.js`'s existing exclusion) and adding all three generated files to `GITHUB_GITIGNORE`. If this project's own `.gitignore` ever starts tracking a real git repo, it should get the same three entries.

## Known Quirks & Gotchas

1. **Underscore normalization is one-way** — see Data Flow above.
2. **Night mode doesn't apply to Custom theme** — it's already fully user-controlled; inverting it would be surprising.
3. **Drag-to-disable is discoverable via tooltip only** — hover an image card to see the shift+drag hint. Intentional, not a bug.
4. **Master Tags mini-grid and main gallery stay in sync bidirectionally** — `renderMasterMiniGrid()`.
5. **Achievement popups auto-dismiss after 5 seconds, no close button** — Settings toggle `achPopupsToggle` disables them entirely.
6. **Dock panels initialize from stored JSON** — if the layout breaks (corrupted JSON), Settings' "Reset panel layout" wipes it back to defaults.
